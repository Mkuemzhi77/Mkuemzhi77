# Глубокий разбор: #1 Игровой маркетплейс / P2P

Учебный клон Steam Community Market / Buff — **без реальных Steam-сделок и чужих аккаунтов**.  
Все предметы и деньги — **виртуальные**, внутри вашей БД.

Оценка из сводки: **8.5** · интерес 8 · опыт **10** · глубина **10** · сложность 9 · демо 7 · риск 7

---

## 1. Что это за продукт одной фразой

Пользователи выставляют цифровые предметы на продажу и покупают их через **ордера** (Buy / Sell).  
Система должна **атомарно** сматчить совместимые ордера, перевести предмет и деньги и не дать продать один предмет дважды.

---

## 2. Зачем брать именно этот проект

| Плюс | Почему важно |
|------|----------------|
| Топ для backend-собесов | Order book, транзакции, race conditions — любимые вопросы |
| Чёткая сложность | Легко объяснить: «как не продать один скин двум людям» |
| Модульная архитектура | Хорошо делится на двоих |
| Растёт постепенно | MVP простой → потом стакан, escrow, история |

| Минус | Как не умереть |
|-------|----------------|
| Демо скучнее кейсов | Сделайте нормальный UI каталога + live-ленту сделок |
| Легко закопаться в «идеальную биржу» | Жёсткий MVP на 3–4 недели |
| Серые товары (аккаунты/ключи) | Только свои виртуальные item_id |

---

## 3. Пользовательские сценарии (что должно работать)

### Happy path
1. Регистрация / логин → стартовый виртуальный баланс + пара предметов в инвентаре  
2. Продавец: «продать AK-47 Redline за 100» → **Sell order**  
3. Покупатель: «купить Redline до 100» → **Buy order**  
4. Движок матчит → сделка → предмет у покупателя, деньги у продавца  
5. Оба видят сделку в истории  

### Опасные сценарии (тут весь сок)
- Два покупателя одновременно жмут «купить» один listing → **побеждает один**  
- Баланса не хватает в момент матча → ордер не исполняется / частичный отказ  
- Продавец отменяет ордер, пока идёт покупка → нет «висячего» предмета  
- Повторный клик / retry сети → **нет двойного списания** (идемпотентность)

## 4. Архитектура (модульный монолит)

На старте **не микросервисы**. Один backend, чёткие модули:

```
┌─────────────────────────────────────────────────────────┐
│                     API Gateway / HTTP                   │
├──────────────┬──────────────────┬───────────────────────┤
│ Auth & Users │ Inventory        │ Trading Engine (CORE) │
│ JWT/OAuth    │ предметы юзера   │ orders + matching     │
├──────────────┼──────────────────┼───────────────────────┤
│ Wallet       │ Market Catalog   │ Escrow / Ledger       │
│ баланс       │ предметы/цены    │ заморозка + перевод   │
└──────────────┴──────────────────┴───────────────────────┘
         │                │                 │
         └────────────────┴─────────────────┘
                          │
              PostgreSQL (+ Redis optional)
```

### Модули и ответственность

| Модуль | Делает | Не делает |
|--------|--------|-----------|
| **Auth** | регистрация, JWT, профиль | торговлю |
| **Inventory** | владение предметами, lock предмета на ордере | матчинг |
| **Wallet** | баланс, hold/release/capture | UI |
| **Trading Engine** | создание ордеров, match, статусы | красивый фронт |
| **Escrow/Ledger** | журнал операций (кто→кому, сколько) | бизнес «какой скин» |
| **Catalog** | справочник предметов, rarity, картинки | ордера |

## 5. Ключевые сущности (схема БД)

### Упрощённая модель

```
users
  id, email, password_hash, created_at

items          -- справочник (AK Redline, …)
  id, slug, name, rarity, image_url

inventories    -- что у кого лежит
  id, user_id, item_id, status  -- available | listed | locked
  UNIQUE или аккуратные ограничения на «один экземпляр»

wallets
  user_id, balance, held_balance

orders
  id, user_id, side (buy|sell), item_id,
  inventory_id NULLABLE,   -- для sell: какой именно экземпляр
  price, status (open|partial|filled|cancelled),
  created_at

trades
  id, buy_order_id, sell_order_id, item_id,
  price, buyer_id, seller_id, created_at

ledger_entries  -- аудит денег
  id, trade_id, user_id, amount (+/-), kind, created_at
```

### Важные инварианты
1. Предмет в статусе `listed` принадлежит **ровно одному** open sell-order  
2. `balance + held_balance` согласованы с ledger  
3. Trade создаётся **только** вместе с переводом предмета и денег в одной транзакции  
4. Один inventory row не может уйти двум покупателям

## 6. Trading Engine — сердце проекта

### Простой MVP-матчинг (хватит на учёбу)

Не строить NASDAQ. Для MVP:

**Вариант A — Listing model (проще, как Buff lite)**  
- Продавец создаёт listing по фиксированной цене  
- Покупатель жмёт Buy Now  
- Транзакция: проверить listing open + баланс → списать/перевести → закрыть listing  

**Вариант B — Order book (сложнее, как Steam Market)**  
- Есть buy orders и sell orders  
- При новом ордере ищем лучший противоположный  
- Match если `buy.price >= sell.price`  

**Рекомендация:** начните с **A**, потом добавьте buy orders (B).  
Так быстрее появится рабочее демо, а собесовая тема «матчинг» всё равно будет.

### Псевдокод атомарной покупки (вариант A)

```text
BEGIN TRANSACTION  (isolation: Repeatable Read или Serializable / SELECT FOR UPDATE)

1. Залочить listing FOR UPDATE
2. Если status != open → abort
3. Залочить buyer wallet FOR UPDATE
4. Если balance < price → abort
5. buyer.balance -= price
6. seller.balance += price
7. inventory.user_id = buyer; inventory.status = available
8. listing.status = filled
9. insert trade + ledger entries

COMMIT
```

### Где ловят гонку
Два запроса одновременно на один listing → без `FOR UPDATE` / unique constraint оба проходят шаг 2 → **double spend предмета**.  
Именно это покрываете интеграционным тестом.

## 7. Escrow / заморозка средств

Зачем: покупатель создал buy order на 100, деньги не должны потратиться на другое, пока ордер открыт.

Состояния денег:
- `available` — можно тратить  
- `held` — заморожено под ордер  
- при match: `held → продавцу`  
- при cancel: `held → available`  

State machine ордера:

```
open → filled
open → cancelled
open → partial → filled     (если позже добавите частичное исполнение)
```

## 8. API (черновик)

```
POST   /auth/register
POST   /auth/login

GET    /me
GET    /me/inventory
GET    /me/wallet

GET    /catalog/items
GET    /market/listings?item_id=

POST   /market/listings          # создать sell
DELETE /market/listings/:id      # отмена

POST   /market/listings/:id/buy  # Buy Now (MVP)

POST   /market/buy-orders        # этап 2
GET    /market/trades
GET    /market/trades/:id
```

Идемпотентность: заголовок `Idempotency-Key` на `buy` — повтор того же ключа не создаёт вторую сделку.

## 12. Тесты, без которых проект «фейковый»

Обязательный набор:
1. Успешная покупка меняет владельца и балансы  
2. Покупка без денег → 402/400, listing остаётся open  
3. Отмена listing продавцом  
4. **Параллельные 2–N покупок одного listing → 1 filled, остальные ошибка**  
5. Повтор buy с тем же Idempotency-Key → одна сделка  

Эти 5 тестов — главный артефакт для собеса.

## 13. Что говорить на собесесе о проекте

Короткий питч:

> «Сделал P2P-маркет цифровых предметов: листинги, атомарная покупка, кошелёк и журнал операций. Главная задача — исключить double-sell при параллельных запросах через транзакции Postgres и интеграционные тесты на гонки.»

Готовые углубления:
- `SELECT FOR UPDATE` vs optimistic locking (`version`)  
- Почему Serializable может быть overkill  
- Зачем нужен ledger, а не только поле `balance`  
- Идемпотентность платежных операций
